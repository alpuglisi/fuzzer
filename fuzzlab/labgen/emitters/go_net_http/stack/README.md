# `go_net_http` skeleton — provenance

**Source:** a real `go mod init fuzzlab-go-net-http-lab` (Go 1.24.7 toolchain,
this sandbox's pinned `go`), run inside `skeleton/` on 2026-09-22, followed
by a hand-written `main.go` — the standard-library equivalent of a
`net/http`-only "hello world" service (no `express-generator`/`rails new`
equivalent exists for this stack, since Go's standard library needs no
project generator to produce a real, runnable HTTP service).

**Trim list:** none. A bare `go mod init` produces exactly one file
(`go.mod`) with no dev-only tooling, test scaffolding, or example code to
strip — unlike `composer create-project`/`rails new`/`npm init`'s fuller
generator output, this skeleton's provenance is genuinely minimal from the
start.

**Deliberate divergences from the raw `go mod init` output:**
- `go.mod`'s `go` directive was widened from the exact pinned toolchain
  version (`1.24.7`) to the minimum minor version this skeleton actually
  needs (`1.22`, for `net/http.ServeMux`'s method-prefixed route-pattern
  syntax, `"POST /path"`, added in Go 1.22) — a real build host running any
  Go ≥1.22 can build this skeleton, not only the exact sandbox version it
  was authored on.
- `main.go` is new, hand-written (not generated by any tool): wires
  `net/http.NewServeMux()`, calls the generated `registerRoutes(mux)`
  (defined in the manifest-rendered `routes_generated.go` this skeleton is
  overlaid with — see `fuzzlab.labgen.emitters.go_net_http`'s module
  docstring), and serves on `127.0.0.1:$PORT` (default `8080`), matching
  every other stack's own loopback-only, env-`PORT`-configurable
  convention (`GoLiveBootHarness` overrides `PORT` per run to avoid port
  collisions across concurrent test runs, the same pattern
  `RailsLiveBootHarness`/`LiveBootHarness` already use).
- `webhookSecret` (a fixed, hardcoded shared secret) is new, Phase-A-only:
  every other stack's skeleton similarly hardcodes a lab-only fixed value
  (e.g. a fixed SQLite path) rather than modeling real secret management,
  which is out of scope for a target lab whose secrets exist only to make
  a payload differential observable, never to be kept secret from this
  project's own fuzzing harness.

**What is deliberately *not* here yet (Phase B, not this dispatch):** a
per-run database (this Phase A's one illustrative cell is stateless — see
`CC-LAB-0170`'s explicit scope call), a real router/framework dependency
(deferred until/unless a Phase-B shape actually needs one beyond
`net/http.ServeMux`), and the richer EventSub message-ID/timestamp/replay-
window checks `docs/research/site-architecture-survey-functionality-twitch.md`
§2 named as Phase B follow-up work alongside the CWE-918 SSRF pick.
